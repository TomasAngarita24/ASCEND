# Technical Decisions

Important technical decisions will be documented here as the project develops.

## Database Technology

**Decision:** ASCEND will use PostgreSQL for persistent application data.

**Status:** Decided

The initial data model is documented in [Database](database.md). Prisma migrations remain to be defined.

## Database Access and Migrations

**Decision:** ASCEND will use Prisma as its ORM and migration tool for PostgreSQL.

**Status:** Decided

The initial Prisma schema and migration live in `backend/prisma/`. Database changes should be made through Prisma migrations rather than manual schema changes.

## Identifier Generation

**Decision:** Primary keys will use UUID v4 values generated by PostgreSQL with `gen_random_uuid()`.

**Status:** Decided

## Data Deletion

**Decision:** ASCEND will use permanent deletion. Every foreign-key relationship will use `ON DELETE CASCADE` so dependent data is permanently removed with its parent record.

**Status:** Decided

This decision means there is no soft deletion or retained audit history for deleted data.

## Default Values

**Decision:** PostgreSQL will generate UUID v4 identifiers and initial timestamps. New workouts will default to `active`; new sets will default to the `normal` type and an incomplete state.

**Status:** Decided

The complete default-value list is documented in [Database](database.md).

## Index Strategy

**Decision:** Initial indexes will support account lookup, exercise discovery, custom exercises, routines, active workouts, workout history, and ordered retrieval of exercises and sets.

**Status:** Decided

The complete index list is documented in [Database](database.md) and should be reviewed against real query patterns after implementation.

## Authentication

**Decision:** ASCEND will use email-and-password authentication with Argon2id password hashing, short-lived JWT access tokens, and opaque refresh tokens.

**Status:** Decided

- Access tokens expire after 15 minutes.
- Refresh tokens expire after 30 days, are stored only as hashes, and are rotated after every use.
- A refresh-token session is permanently deleted on logout or rotation.
- Tokens are stored in secure device storage, never in AsyncStorage.
- Protected backend operations authorize access by the authenticated user identifier.

The detailed contract is documented in [API](api.md), and the session data model is documented in [Database](database.md).

## Code Quality

**Decision:** ASCEND code will follow consistent formatting and maintain clear separation of responsibilities. The shared `.editorconfig` defines the baseline formatting rules.

**Status:** Decided

Backend application setup is separated from process startup so the application can be tested and extended without coupling it to the listening server.

## Local PostgreSQL Environment

**Decision:** Local PostgreSQL development will run through Docker Compose using the versioned `compose.yaml` configuration.

**Status:** Decided

The configuration uses a persistent Docker volume and a healthcheck. Database credentials are supplied through the ignored root `.env` file, based on `.env.example`.

## Automated Testing

**Decision:** Backend integration tests use Node's native test runner and exercise the Express application with the local PostgreSQL database.

**Status:** Decided

Tests create and remove isolated temporary data so they can validate real authentication behavior without preserving test accounts.

## Estimated One-Rep Maximum

**Decision:** ASCEND will estimate one-repetition maximum using the Epley formula: `weight * (1 + repetitions / 30)`.

**Status:** Decided

The estimate uses completed sets with recorded weight and repetitions. ASCEND returns the highest value for the requested exercise, rounded to two decimal places.
